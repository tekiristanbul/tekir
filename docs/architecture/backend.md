# backend

## goal

define how [[api]] and [[db]] get deployed and operated for a solo, currently-unfunded founder. the initial deployment minimizes operational ownership rather than maximizing infrastructure sophistication.

## decisions

### service shape

- **api service**: go handler → service → repository, shipped as one stateless container image.
- **notification worker** (implemented — issue #78, `cmd/notifier`): same repository, separate binary/process polling `notification_outbox` and dispatching pushes for needs-help updates only. fcm remains the eventual mvp-selected push vendor, but no real provider is wired yet — see "auth / security" below.
- no microservices or external message broker are required for mvp.

### data layer

- **postgres + postgis**: digitalocean managed postgresql.
- **media storage**: digitalocean spaces through the s3-compatible api (implemented — issue #89). application code depends on the s3 api rather than a digitalocean-specific storage sdk.
- backups, failover, and database upgrades are managed by digitalocean rather than self-hosted by the project.

### deployment

- api and notification worker deploy to digitalocean app platform as separate components built from their container definitions.
- github actions is the ci/cd system.
- mvp traffic is expected to run without kubernetes.
- kubernetes migration is reconsidered only after sponsorship or external funding provides a reason and budget to own the additional platform complexity. traffic growth alone may still be handled first by app platform scaling.
- no gateway api, cert-manager, self-hosted postgres operator, or cluster lifecycle platform is part of mvp.

### auth / security

- short-lived jwt `access_token` plus a hashed, revocable `refresh_token` after otp verification (implemented — issue #58).
- otp is provider-neutral behind two boundaries (implemented — issues #58/#59), selected via `OTP_PROVIDER`: `fake` keeps the deterministic, no-network, log-only local flow (`SmsSender` + backend-generated codes in `otp_codes`), and `twilio` routes both code delivery and code checking through twilio verify (`OTPVerificationProvider` / `TwilioVerifier`) — verify owns generation, delivery, expiry, resend cadence, and guess limiting end to end, so none of the local `otp_codes` machinery runs on that path. selection is environment-gated and fail-closed: `fake` (including the unset-provider default) is only reachable under an explicit `APP_ENV=development`; every other environment — `production`, unset, or unrecognized — accepts only `twilio` and fails startup on `fake`, unset, unknown, or a `twilio` selection missing any of `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_VERIFY_SERVICE_SID`. there is deliberately no runtime fallback from a selected `twilio` provider to `fake`, ever. twilio verify addresses a verify service sid, not a sender number — `TWILIO_NUMBER` is unused. the adapter maps every twilio outcome onto the existing auth error contract (invalid phone, invalid code, expired/replayed, throttled, and — for timeouts, outages, or runtime credential rejection — the same generic internal error any dependency outage produces), retries at most once and only for known-safe transient failures (a 5xx response or a dial error; never a timeout, which may already have sent an sms), propagates request cancellation to the outbound call, and never logs phone numbers, codes, sids, tokens, or raw response bodies. operational notes: rotating the auth token is a deployment-secret change plus restart (startup only validates presence, so a bad value surfaces as logged `401` mapping to internal errors — watch for `twilio verify rejected the configured credentials`); rollback is redeploying with the previous secret; a twilio outage degrades logins to retryable internal errors without touching the rest of the api.
- media storage is hidden behind an `ObjectStore` interface (implemented — issues #70/#89), mirroring `SmsSender`/`OTP_PROVIDER` exactly, selected via `OBJECT_STORAGE_PROVIDER`: `fake` keeps the deterministic, local-disk dev/test provider (`FakeObjectStore`; `MEDIA_LOCAL_DIR` sets where it reads/writes, and the api serves its objects back at `GET /v1/media/objects/{key}` ([[api]]) so a local walkthrough can view an uploaded photo without a real account), and `s3` stores media in real s3-compatible object storage (`S3ObjectStore`) — digitalocean spaces for 0.1, but the adapter is standard sigv4 over `PutObject`/`DeleteObject` with no spaces-specific sdk, signed locally over net/http exactly like the twilio and fcm adapters wrap their vendors. selection is environment-gated and fail-closed like the other providers (`config.ResolveObjectStorageProvider`): `fake` — including the unset-provider default — is only reachable under an explicit `APP_ENV=development`; every other environment accepts only a fully configured `s3` (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_BASE_URL`; optional `S3_FORCE_PATH_STYLE`) and fails startup on anything else, with no runtime fallback to local disk, ever. the names are application-owned (`S3_*`, never `AWS_*`) so the process can't pick up unrelated host credentials. objects are public product content ([[privacy]]): uploaded with `x-amz-acl: public-read`, the pipeline-validated content type, and an immutable cache-control policy, under fresh opaque uuid keys that never carry user-provided filenames or personal data; `S3_PUBLIC_BASE_URL` (bucket endpoint or cdn) is what stored urls are built from, so reads never proxy through the api and write credentials never reach clients. `MEDIA_MAX_BYTES` bounds an uploaded file's size before it's ever decoded; `MEDIA_VIDEO_MAX_BYTES` (issue #153) is the equivalent cap for `POST /v1/media`'s optional video path — kept separate and materially larger since a video is stored pass-through rather than re-encoded down like an image, so the same 30-second product cap needs more byte headroom to be reachable at all. failure handling is bounded: per-attempt timeouts derived from the request context, at most one retry and only for transient failures (5xx, 429, dial errors, and — safe here because put/delete are idempotent, unlike twilio's sends — timeouts); a failed database write after upload compensates by best-effort deleting the object, and a failed compensation is logged, never escalated into an orphan database row. nothing sensitive is ever logged: no access keys, signatures, object keys, urls, or response bodies. operational notes: rotating credentials is create-new-key → update deployment secrets → restart → verify an upload → revoke old key (a bad key surfaces as logged `s3 object storage rejected the configured credentials`); rollback is redeploying with the previous secrets — never a downgrade to `fake` in production; a spaces outage degrades cat creation/media upload to retryable internal errors while already-stored media stays readable from the public endpoint and the rest of the api keeps working; orphaned objects (compensation-delete failures) are found by diffing bucket listings against `media.object_key` and are safe to delete when older than a day — full procedures in DEVELOPMENT.md's "object storage providers".
- short-form video uploads default to muted (implemented — issue #194): `media.muted` is a per-row flag the uploader sets at `POST /v1/media` (the handler defaults it `true` when the request sends nothing, so a video is muted unless the composer's toggle explicitly opts into audio), and every video playback surface in the app reads it back to decide whether to offer an unmute affordance at all. This is a policy flag, not a transcoding instruction: the "no transcoding, stored as-is" decision above is unchanged, so a video's own audio track — muted or not — is stored exactly as uploaded. **Accepted limitation:** because the object is stored pass-through and served from a public url ([[privacy]]), a muted video's audio track is still physically present in the stored object and audible to anyone who fetches that url directly (e.g. in a plain `<video>` tag or media player) rather than through the app's own playback surfaces, which are the only place the `muted` flag is enforced. Removing the audio track at the object level (real transcoding) was explicitly ruled out for this issue — narrower scope, and a decision to make deliberately rather than as a side effect of a UI default — and is left for a separate, future decision if this gap ever needs closing.
- uploaded jpeg photos are corrected for exif orientation before the pipeline's decode→re-encode strips exif entirely (implemented — issue #237): `service.mediaPipeline.process` reads the jpeg's own Orientation tag (`jpegExifOrientation`, a hand-rolled TIFF/IFD0 parser — no exif library dependency, matching this same file's existing hand-rolled iso-bmff video-box parsing) and applies it as a pixel transform (`applyExifOrientation`) before the existing re-encode step, so the canonical stored image is upright regardless of what the source camera/gallery app wrote, and the re-encoded output itself carries no orientation tag to cause a second, downstream rotation. There is still no separate thumbnail/derived-image asset to keep in sync: the one canonical re-encoded object this pipeline produces already serves every rendered surface ([[api]], [[db]]), so correcting orientation here fixes all of them at once. png carries no orientation convention any real capture/gallery app sets, so it's left unmodified. **Accepted limitation:** media uploaded before this fix already had exif — including Orientation — irreversibly stripped at upload time by the pre-#237 pipeline, and the pre-processing raw bytes were never retained anywhere (object storage only ever held the re-encoded output); there is no original to recover orientation from, so existing stored media is left untouched rather than guessed at. A photo uploaded before this fix that rendered sideways keeps rendering sideways until re-uploaded.
- push delivery is hidden behind a `NotificationSender` interface (implemented — issues #78/#84), mirroring `SmsSender`/`ObjectStore`, selected via `NOTIFICATION_PROVIDER`: `fake` keeps the deterministic, no-network, log-only dev/test sender, and `fcm` sends real pushes through firebase cloud messaging http v1 (`FCMNotificationSender`) authenticated with a service-account json referenced by `FCM_CREDENTIALS_FILE` (the firebase project id comes from the file's `project_id`; legacy server keys are deliberately unsupported). selection is environment-gated and fail-closed exactly like `OTP_PROVIDER` (`config.ResolveNotificationProvider`): `fake` — including the unset-provider default — is only reachable under an explicit `APP_ENV=development`; every other environment accepts only a fully configured `fcm` and fails `cmd/notifier`'s startup on anything else, with no runtime fallback to `fake`, ever. the sender classifies fcm outcomes: a permanently rejected registration token (unregistered/invalid/sender-id mismatch) retires that device's `push_token` (token-matched, so a concurrently refreshed token survives) while the in-app `notifications` row — created unconditionally for every recipient device, token or not — remains the source of truth; transient failures (5xx, 429, timeouts) are retried at most once and only when known-safe (5xx or dial error, never a timeout), then logged and skipped under the outbox's existing at-most-once policy. clients register/refresh their fcm token via device-authenticated `PUT /v1/devices/me`, which updates the caller's own row in place and clears the same token off any other row, so a re-registered installation can never be pushed twice. nothing sensitive is ever logged or exposed: no registration tokens, credentials, message ids, or recipient lists.
- pre-publication content moderation is hidden behind a `Moderator` interface (implemented — issue #241), mirroring `SmsSender`/`ObjectStore`/`NotificationSender` exactly, selected via `MODERATION_PROVIDER`: `fake` keeps the deterministic, no-network dev/test provider (`FakeModerator` — fixture-triggered allow/reject/unavailable outcomes, never real content judgment), and `cloudflare` calls Cloudflare Workers AI (`CloudflareModerator`) with the configured `MODERATION_TEXT_MODEL`/`MODERATION_VISION_MODEL` slugs — model identifiers are deployment configuration, never a public api/domain concept. selection is environment-gated and fail-closed exactly like the other three providers (`config.ResolveModerationProvider`): `fake` is only reachable under an explicit `APP_ENV=development`; every other environment accepts only a fully configured `cloudflare` (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, plus both model slugs) and fails startup on anything else, with no runtime fallback to `fake`, ever — startup only validates presence/syntax, never a live model call. `CatsService`/`MediaService` each default their own `moderator` field to `FakeModerator{}` when the `WithCatsModerator`/`WithMediaModerator` constructor option is omitted, purely so the pre-existing test suites that don't exercise moderation keep compiling unchanged; this default is never reachable in production, where `cmd/api/main.go` always supplies the environment-resolved provider explicitly and `ResolveModerationProvider` already fails startup outright on misconfiguration before either service is constructed. tekir owns the allow/reject policy: both models classify content only against a fixed, application-owned category vocabulary embedded in this package's own fixed prompts (`moderationTextPrompt`/`moderationImagePrompt`) — never a raw vendor taxonomy — and a model's raw text reply is strictly parsed as `{"decision":...,"categories":[...]}`; malformed/unparseable output, a timeout, or a transport failure all fail closed identically as `ErrModerationUnavailable`, exactly like `ErrContentRejected`, before `ObjectStore.Put`/the write ever runs, so nothing unreviewed is ever stored or published. video moderation samples 3 deterministic frames (near start/middle/near end, `FrameExtractor`/`FFmpegFrameExtractor`) via a real `ffmpeg` binary shelled out to in-process, composes them into one contact sheet in pure Go, and classifies that single sheet through the same vision-model path as a photo — there is no separate video-specific model call, and no persisted moderation state machine, queue, or async publication flow. **accepted tradeoff:** `ffmpeg` is a new runtime dependency the prior `gcr.io/distroless/static-debian12` container image can't host (no package manager, no shared libraries) — `backend/Dockerfile`'s final stage moved to `debian:12-slim` with `ffmpeg`/`ca-certificates` installed via `apt-get`, trading some of distroless's minimal attack surface for a real, auditable os package rather than an unverified third-party static ffmpeg binary. normal ci runs only against the deterministic `fake` provider; the `cloudflare` provider is a separate, manually-triggered release-gate smoke suite (DEVELOPMENT.md "content moderation providers") never exercised by automated ci.
- provider credentials are deployment secrets and never committed to the repository.
- device identity is used for installation association, push delivery, and account linking; contribution authorization follows [[api]] and [[trust]].

### observability

- structured logging and basic prometheus-compatible metrics for request rate, latency, failures, and worker queue depth.
- distributed tracing is not required for mvp.

## open questions

- none for mvp. concrete digitalocean plan sizes, region, retention settings, and twilio pricing configuration are deployment-time configuration rather than product or architecture questions.

## out of scope

- kubernetes, gateway api, cert-manager, cnpg, or any self-hosted operator.
- multi-region or disaster-recovery design.
- azure services.
- replacing twilio unless cost, deliverability, or regulatory evidence requires a new provider decision.
